# stage.dobeworks.com

**Carry the Stop** is the public front door: a deterministic launch-control game in which a fictional ELIZA · COLOSSUS · GUARDIAN agent produces each candidate, while the player controls prompts, inspections, finding custody, handoffs, acceptance or override, and vehicle preparation. Three fixed packets run from cold thrusters through a NASA-style T−010 countdown and the full authored T+000–100 profile. A packet that reaches ignition with an error produces the corresponding simulated flight consequence.

The agent's responses are pre-authored branches bundled with the site. The browser receives prompt labels, not the hidden response mapping, and cannot write candidate values, gate decisions, clocks, or flight state. The server creates immutable candidate revisions, binds check receipts to them, runs the real frozen DobeWorks inventory and DEGS evaluation at their explicit boundaries, and owns countdown and flight progression. Play requires no model provider, search, remote media, or third-party runtime request.

The earlier **Zariner · Save the Signal** arcade and deeper fictional engineering desk remain intact at `/classic`. That exercise carries one small, consequential defect through DobeWorks, DEGS, repair, human acceptance, and a twelve-second one-button Venus run. It is inspired by the missing R-bar described in NASA's account of Mariner 1, while using a fictional vehicle and original teaching note. The preserved desk also contains a second case that changes one character from `0` to `1` inside a 19,581-byte, 284-line NASA/JPL F´ source pair. Both checked cases stop before launch and remain inspectable beside their corrected packets.

The source packet contains the actual NASA/JPL F´ `TableGenerator.c`, `Crc32.cpp` and license, plus an explicit requirement, source identities and fictional telemetry/evidence. The component supports data integrity; this exhibit does not run flight guidance or vehicle control. The wider mission and all role decisions are fictional.

The existing Render Starter service and disk serve all three hostnames. No new paid service, model provider or per-visitor AI call is required. Existing hosting bandwidth/resource charges still apply. Dialogue is an original keyword/no-match script inspired by [Weizenbaum's 1966 ELIZA paper](https://doi.org/10.1145/365153.365168); it cannot change an engine result or a mission receipt.

## Current front door: prompt, inspect, carry, launch

Easy, Medium, and Hard each begin with an autonomous draft. The player can prompt the agent to produce another immutable revision, run the packet's named checks, choose the exact receipts and findings that travel in the outgoing record, and stage the active candidate. DobeWorks returns `COMPLETED_UNACCEPTED` / `NOT_PERFORMED`. DEGS then evaluates the warning fields in that exact projected record. The player separately accepts a passing record or deliberately overrides a stop before conditioning, arming, and igniting the fictional vehicle.

Record quality and physical flight are separate axes. Carrying an unresolved finding produces a real `BLOCKED` DEGS decision. Omitting it demonstrates the adapter defect explicitly rather than crediting DEGS with knowledge it never received. A human can still override a blocked record; the resulting flight follows the frozen candidate. Candidate, configuration, observation, receipts, record, worker result, DEGS result, and human authority remain bound in the server-owned launch snapshot.

Easy has one condition and one wind-balance check. Medium adds a unit-conversion trap. Hard adds archived and current observations, two coordinate frames, two clocks, and three candidate-bound checks. T−010 begins only from a frozen accepted or overridden record; engine start occurs at T−006. A prestart hold freezes the countdown. A poststart hold aborts and safes the vehicle. All events stop after a terminal state, and retry retains the completed run.

## Preserved classic: find, carry, fix, fly

The preserved classic is a four-part arcade loop: find the missing mark in a moving guidance strip; keep its warning attached while completion signals compete for attention across three handoffs; watch DobeWorks stage the completed but unaccepted work and DEGS close the gate; repair and separately accept the corrected packet; then guide the fictional successor through three telemetry gates. Its first packet omits the combining overbar from the required `R̅`. Losing the warning during translation produces one immediate fictional loss. After the real gate blocks the packet, a smaller **WHAT IF: APPROVE FAILED** branch shows the separate consequence of human override without changing the active BLOCKED decision or recording acceptance. Fixing the mark preserves the failed candidate beside the corrected record. Win, loss, and flight-replay paths are immediate. A compact optional post-win terminal summarizes the four decisive commands without reopening the text-heavy engineering desk.

The active playfield contains one dominant object and one dominant action. Labels during play are short; explanation and NASA links are collapsed until after the run. The normal flight uses hold/tap/Space/Enter as one input. Reduced-motion mode replaces continuous flight with three discrete gate-clear actions, and the initial search offers an untimed mode. No cue depends on sound, and this release contains no audio.

The note is an original teaching reconstruction of the notation loss described in NASA's Mariner 1 account, not recovered guidance code. A small exact-reference check detects the omitted combining overbar in `handoff/guidance-note.md`. DobeWorks performs its real bounded synthetic inventory and retains `COMPLETED_UNACCEPTED` / `NOT_PERFORMED`. The exhibit adapter supplies a structured unresolved warning to the real DEGS CLI. A corrected note supplies consistent `NONE` / `RESOLVED` / `resolved=true` warning fields and an evidence path, rather than silently deleting the warning. Readiness then passes; visitor acceptance remains a separate simulation step. The Worker result itself is not promoted.

DobeWorks and DEGS enforce the record they actually receive; they do not invent missing findings or supersede human authority. Protection therefore depends on checking the intended package, preserving the resulting warning through translation, and refusing to approve a failed or unaccepted result. The two arcade loss paths show those distinct limits: a warning can be lost before the gate receives it, or a human can override a correctly blocked failed package.

The evidence includes a controlled comparison that keeps the candidate note and all other task fields fixed, dropping only the warning field in a separate read-only DEGS evaluation. The preserved record is BLOCKED; the completion-only record returns PASS because it no longer contains the stop. The comparison never replaces the active gate result or records acceptance.

The mission also names three stop conditions from the submitted AgentVerify abstract: a stale observation, an unresolved warning, and unaccepted output. The current warning and acceptance states update as the visitor proceeds. A rule-based guide answers questions about DobeWorks, DEGS, and the blocked decision; its answers remain deterministic and cannot change evidence or results.

The note, historical context, acceptance requirement and source reference remain inspectable. Correction retains the original failed candidate in evidence.

The page translates the same handoff rule into three ordinary applications. A DOI resolver can find a citation mismatch, a comparison can find an instruction lost between AI windows, and a test, review, or person can find a software defect. DobeWorks stages the completed work without promotion, an adapter carries the supplied finding in the handoff record, and DEGS enforces its stop; neither engine is presented as a universal detector.

## Rocket workflow

1. Configuration engineer: establish the bounded notation or CRC32 source package and requirement.
2. Telemetry engineer: inspect the real Observer's fresh/stale synthetic fixture result.
3. Package engineer: stage the real Worker's synthetic inventory of Markdown source summaries. Inspect its staged-only contract and unaccepted result. Independently check either the required notation against its supplied reference or the candidate component's known-answer CRC behavior. Show the exact failure and downstream stop, then choose to hold, inspect a bypass, or correct the packet.
4. Verification engineer: inspect retained results from the frozen repositories' existing core tests, run once during release preparation through their shared interface adapter. Preserve counts, commands, stdout, stderr and Python version. Reparse the captured test output and check source identity before accepting the prepared record.
5. Independent reviewer: open the real DEGS read-only handoff decision, previous receipts and core verification. Opening the report does not accept the package; a separate action records the visitor's fictional acceptance after the checks pass.
6. Launch readiness: the Weather Officer reviews the fixed observation against a 15-knot wind limit. T+00 holds at 22 knots; receiving the T+05 observation supplies 9 knots, after which the officer can record weather GO for that window. The Launch Director then sees one readiness summary containing package acceptance, the weather decision, and the remaining blocking item. Only the director can authorize the simulated countdown.
7. Run the successful simulated flight after all handoffs and the complete poll. A separately labelled what-if branch illustrates a launch with the known checksum error while preserving the real BLOCKED decision and leaving package acceptance and successful-flight state unset.
8. View the recorded evidence inline. No checks rerun and no program downloads a file.

The second selectable case uses a quiet transcription error: its received copy changes exactly one ASCII character in `TableGenerator.c`, line 44, from `0xEDB88320` to `0xEDB88321`. The original telemetry's CRC can still be intact while its proposed generating component is wrong.

## Engine and privacy boundaries

`StageHost` routes only `stage.dobeworks.com` to a separate ASGI app. Lab login, inboxes, jobs, messages, SQLite and credentials are absent from its routes. Other hosts continue into the existing bridge.

`stage_vendor/sources.json` freezes selected runtime files, tests, fixtures, support files and notices at these default-branch heads, checked on 2026-10-21:

- DobeWorks: `ab7fd6019b6a8ae799213d485dea1d77eb2ed2ce`
- DEGS: `29632112ea809e7a589bf04031ecb433ec169888`

These files are unmodified. The selected engine runtime files still match the earlier `initial-release-final` snapshots; the DobeWorks interface and voice-bank files now come from the later verified-voice commit identified above. `check_sources()` verifies every selected file before a run. No runtime GitHub fetching or automatic upstream updates occur. The existing shared interface's task adapter, strict CLI result decoder, test commands and test summary parser are reused. DEGS evaluates the submitted read-only record; it does not independently inspect packet files. The exhibit performs the manifest comparison and maps a failed comparison to a blocked record. Worker output remains `COMPLETED_UNACCEPTED`, promotion `NOT_PERFORMED`; the separate simulated reviewer receipt does not promote that engine output or authorize real execution.

NASA/JPL F´ is pinned at `a37ffa40871e567481d0a7626c12b24d8acdbf15`. Preparation compiles its real C99 table generator and compares all 1,024 values to the pinned C++ reference. The exhibit's small checksum loop checks `123456789 → CBF43926` before using the generated table. Caltech's Apache-2.0 header and Stephan Brumme's embedded notice are retained. Full provenance is in `stage_vendor/nasa-fprime/`; no NASA endorsement is claimed.

Visitor progress is held in at most 256 temporary in-memory sessions, retained across reloads, and expires after two idle hours or server restart. Sessions use a random host-only HttpOnly SameSite cookie, Secure on HTTPS, and CSRF tokens. There is no stage database, account, visitor upload, analytics, paid AI or stored conversation history. The fixed scenario reports and prepared core verification are shared read-only caches, while visitor candidates, receipts, records, gates and runs remain separate.

The launch API accepts only listed prompt IDs, check names, existing candidate/receipt/finding references, and enumerated actions in bounded JSON requests. Sixty POSTs per minute globally, a 15-second adapter limit, process-group termination, a 128-action run record and a two-hour maximum attempt clock bound work. No visitor-provided code, path, URL, telemetry, clock, candidate value, or shell text reaches a subprocess. Child environments omit bridge credentials. Runtime evidence directories are temporary and removed after fixed checks. Access logs remain disabled. One same-origin JavaScript file renders server state and sends choices; it cannot set a gate decision, acceptance, countdown, or flight result. No remote font, script, media, model, or per-visitor service is loaded. The classic interface retains its separately bounded form workflow.

## Build and verify

```sh
python stage_mission.py --prepare
python -m pytest -q tests
```

Preparation runs both core suites with the shared interface's 120-second per-suite limit and rejects failures. A compiler is needed only for preparation. `tables.json` is generated and ignored by Git. Runtime checks compare it to the pinned reference; it can be prepared before transfer. The generated core-verification record is also ignored by Git. Core suites are standard-library `unittest`, invoked using the vendored shared interface's `core_test_commands()`.

The normal Git build is still recorded in `render.yaml`. If Git deployment is unavailable, `deploy_from_disk.py` supports a deliberately prepared release directory on the existing `/var/data` disk and a digest-pinned official Python 3.12.14 Linux image. Prepare this repository and pinned requirements in that directory's `packages/`, verify NASA tables and tests on the host, then retain the host-generated core verification and configure its Docker command to `python /var/data/stage-release/RELEASE/deploy_from_disk.py`. The launcher drops to the existing UID/GID 1000, preserves the bridge environment and SQLite path, and never installs or fetches code at startup. The image deployment sets `FORWARDED_ALLOW_IPS=*` so Uvicorn recognizes HTTPS from Render's terminating proxy. Blueprint Auto Sync is set to No to preserve this deliberate image configuration; the normal Git blueprint remains available for a future deliberate return to Git deployment. The source bundle digest and image digest identify this deployment, rather than Render's old Git commit display. No additional service, disk or registry account is needed. Source/image changes require a deliberate deployment.
